一、案例分析题30 分 · 每题 6 分

第 1 题（6 分）· 你是技术美术第 1、4、7 章

美术在 3ds Max 里做了一个主角，导出 .fbx 交给你。你要让他在 Unity 里能动、能穿、能打。

  1. 模型拖进工程后，第一件要检查的是什么？要让同一套动作能复用到别的角色上，必须做什么？
  2. 角色身上的贴图有三张，程序问你这三张分别是什么类型，导入设置上有什么区别？
  3. 角色有「身体 / 衣服 / 武器」三块，材质球要怎么组织才不至于拖慢帧率？
参考答案第 1 章 · 资源导入｜第 4 章 · 贴图与材质｜第 7 章 · Avatar

① 先查朝向和缩放，再做 Avatar。3ds Max 是 Z 轴向上，Unity 是 Y 轴向上，导进来经常是躺着的或转了 90°；缩放也要核对，模型单位不一致会让角色变成巨人或蚂蚁。这两项在模型的 Import 设置里改，不要靠后面调 Scale 硬拉——硬拉会让物理和碰撞体的数值全部失真。然后是最关键的一步：把 Rig 的 Animation Type 设为 Humanoid，Unity 会据此生成 Avatar（替身），也就是把模型自己的骨骼映射到一套标准人形骨架上。生成了 Avatar 才能做 Retargeting（动画复用）——同一套走路、攻击动作可以直接给别的角色用，不用重新做。生成后要打开 Configure 界面看一眼，骨骼映射有红叉就说明没对上，必须手动拖。

② 三张贴图三种类型。一张是基础色（Albedo / Base Color），Texture Type 用默认的 Default，压缩开、Mipmap 开；一张是法线贴图（Normal Map），Texture Type 必须改成 Normal map——这一步不能省，如果当普通贴图导入，Unity 不会把它转成切线空间的法线格式，表面的凹凸方向会全部出错，光照一打就发现凹凸是反的；第三张是高光 / 遮罩（Specular / Metallic），要注意把它在导入设置里关掉 sRGB（Color Space 选 Linear），因为它是数据图不是颜色图，按颜色处理会让数值失真。另外三张图要共用一套 UV，UV 是在建模软件里展开好的，进 Unity 只是按 UV 采样。

③ 材质合并成一套。三个部件不要各给一个材质球。每个材质球在渲染时就是一次 Draw Call，一个角色拆成三份，场上二十个角色就是六七十次绘制调用。做法是：三张图打成一张图集（Atlas），角色只用一个材质球、指定一个 Shader，靠 UV 落在图集的不同区域来区分部位。这样场上所有角色可以合批，绘制次数大幅下降。如果确实需要不同质感（比如武器是金属、衣服是布料），那就分成两个材质，但每个材质内部一定用图集。判断标准很简单：材质数量决定 Draw Call 数量，图集是压在最低的那个手段。

第 2 题（6 分）· 你是特效师第 6 章

要做一个技能释放的爆炸：中心一团火光，向外崩碎片，碎片落地后再冒一股烟。这个特效在混战中同时可能出现二十个。

  1. 这个特效至少要用到哪几个粒子模块？「碎片落地后再冒烟」这一步靠什么实现？
  2. 火光从亮黄迅速变橙、最后变成黑烟散去，是哪两个模块配合的结果？
  3. 二十个同时播放怎么保证不掉帧？说出至少四个手段。
参考答案第 6 章 · 粒子系统

① 模块与二级发射。基础模块定 Duration、Start Lifetime、Start Speed；Emission 用 Burst 一次性喷一簇（爆炸不是持续喷，是瞬间爆开，所以不用 Rate over Time）；Shape 用 Sphere 让粒子向四面八方飞；Color over Lifetime 加 Size over Lifetime 做消散；碎片部分再加 Velocity over Lifetime 给它一个抛物线感。「碎片落地后再冒烟」用 Sub Emitters（子发射器）——它能在主粒子的 Birth / Collision / Death 三个时机触发一个新的发射器，这里要的是 Death（碎片消失时）或 Collision（撞到地面时）触发烟雾。这是「一级特效带出二级特效」的标准做法，不需要写代码。

② 颜色两段式。Color over Lifetime 负责颜色本身：新建一个渐变，色标依次摆上亮黄（255,255,200）→ 橙（255,140,0）→ 暗红（120,20,0）→ 黑，同时把 Alpha 从 255 渐到 0，这样它不只是变黑，而是「变黑的同时淡出」。Size over Lifetime 负责体积：先用一条「快速放大再缓慢收缩」的曲线，让火光先炸开再散掉。两个模块叠起来，才有「炸一下、扩出去、散掉」的完整过程。这里用的一定是 over Lifetime 类模块——它描述的是单个粒子从生到死的一生，像花开花落；而 by Speed 类（Color by Speed、Size by Speed）是按速度条件触发，像跑龙套的，用在这里反而不对。

③ 四个手段。第一，Max Particles 设上限，比如 60，超过就自动丢弃，这是防止连续爆炸堆到几千个粒子的最后一道闸；第二，Renderer 的 Render Mode 用 Billboard（面向相机），不要用 Mesh 模式，Net 一个粒子一个网格会把顶点数打爆；第三，把光照和碰撞关掉——粒子的 Lights 模块和 Collision 模块都很贵，混战里不需要每个爆炸都照亮周围、也不需要真的算碰撞；第四，整个特效做成 Prefab 放进对象池，播完 SetActive(false) 还回去，不要在运行时反复 Instantiate/Destroy。再加一条：整套粒子共用一张图集，避免每个粒子系统各占一个材质。

第 3 题（6 分）· 你是角色动画师第 7 章

主角要能边跑边开枪：下半身一直在跑，上半身独立瞄准并开枪，两个动作不能互相打断。

  1. 用什么机制让上下半身各播各的动画？需要配一个什么资源？
  2. 上下半身的切换时机怎么对齐？如果不对齐会出现什么现象？
  3. 如果瞄准还要分左、中、右三个方向，这一层内部该用什么？
参考答案第 7 章 · 动画层与融合树

① 用动画层 + 身体遮罩。在 Animator Controller 左上角新建一层（Layer），第 0 层叫 Base Layer 放跑步、待机这些全身动作，第 1 层叫 Upper Layer 放瞄准、开枪。关键在同一层要挂一个 Avatar Mask（身体遮罩）——遮罩里只勾选上半身的骨骼（脊椎以上、手臂、头），这样第 1 层的动画只驱动上半身，下半身仍然由第 0 层控制。如果不挂遮罩，上层动画会把全身覆盖掉，角色就变成「站着不动光开枪」。层权重用 SetLayerWeight(1, 1f) 打开，权重为 1 表示该层完全生效，0 表示完全被下层覆盖——开枪时从 0 淡到 1 就有了「抬起枪」的过渡。

② 对齐时机，否则会「腿和手打架」。两层各自有独立的时间轴，如果跑步动作的步频和开枪动作的节奏对不上，看起来就像上半身在抽搐、下半身在原地蹬。解决办法有两个：一是给上层勾 Sync 或调整上层的 Speed，让两层的关键帧大致同相；二是干脆让开枪动作不带位移、不带腿部动画，只做上半身的骨骼动画，从源头上避免冲突。不对齐的典型现象是：抬枪的瞬间腿会「卡一下」，因为上层动画在那一帧对下半身也产生了权重影响。

③ 层内用融合树。瞄准的左、中、右不是三个状态之间的切换，而是同一个动作在不同方向上的连续变化，所以该用 Blend Tree：一个 direction 参数（Float，取值 −1 到 1）混合 aimLeft、aimCenter、aimRight 三个动作，临界点设 −1、0、1。玩家往左推摇杆，上半身就平滑偏向左，中间没有硬切。判断标准还是那句：能在「一半左一半中」之间连续变化 → 用融合树；只能是其中之一 → 用状态机。这两者是包含关系，融合树是状态机里的一个特殊类型的状态，不是替代关系。

第 4 题（6 分）· 你是关卡美术第 3 章

要用 Terrain 从零搭一块 500×500 的野外战场：有起伏的丘陵、草地和土路两种地表、成片的树林和草、还要能让草随风摆动。

  1. 从建工程到地形能看，第一步是什么？导入环境包时报了一堆红错，怎么处理？
  2. 「一片丘陵」怎么刷出来？草和树的「距离」参数各自控制什么？
  3. 怎么让草动起来？如果草不动，最可能是哪两处没设？
参考答案第 3 章 · 地形系统

① 先导入 Environment 包。Unity 5.x 之后不再内置标准资源，要先从 Asset Store 或官方下载 Environment 包导入，地形的笔刷贴图、树、草资源都在里面。导入时报错只修「版本相关」的那几个，其余直接 Clear 清除即可——这是课件原话。因为包里带的很多是旧版本 API 的示例脚本，Unity 只是提示它们过时，不影响地形功能；真正会阻断的是「包版本与当前 Unity 版本不匹配」那类，需要按提示升级或换版本。清完之后在菜单里 GameObject → 3D Object → Terrain 建出地形，再把 Terrain 的尺寸改成 500×500。

② 造型与距离参数。丘陵的做法是先定基准再堆细节：Set Height 设一个基准高度（比如 10）→ 用 Flatten 把整片抬平 → 再用 Raise/Lower 局部堆出山脊 → 最后用 Smooth 修坡。先 Flatten 是为了让整块地面高度一致，否则后面怎么刷都是歪的。地表用 Paint Texture → Create Layer 一层层叠：第一层铺草地作为基础层，再叠一层土路用画刷刷出路径。草和树各有自己的距离参数：草的 Detail Distance 是「多远以外的草不再绘制」，Detail Density 是「同一范围内画多少比例」（默认 1，调小则过密的草被跳过）；树的 Tree Distance 是「多远以外的树不再绘制」。这两个是大地形不卡的第一道闸，比减模型面数有效得多。

③ 风区，以及它为什么不动。在场景里加一个 WindZone（独立 GameObject，不是地形的子物体）。Mode 选 Directional 表示整个战场统一朝一个方向吹；如果只想让山谷口那块起风，选 Spherical 并调 Radius 限定范围。风力上，Wind Main 给基础风压，Turbulence 加紊流让风变乱，Pulse Magnitude / Pulse Frequency 控制阵风的强弱和节奏——只调 Wind Main 会得到匀速风，不像自然风。
如果加了风区草还是不动，最可能是两处没设：一是草的渲染设置里没有开启受风影响；二是如果想让粒子（比如落叶、沙尘）也被吹动，粒子系统必须开启 External Forces（外力）模块，不开的话风区对它完全无效。

第 5 题（6 分）· 你是音频设计第 3、8 章

测试时玩家抱怨：「打起来太吵，根本听不出敌人从哪边过来。」

  1. 让音效「有方向感」，AudioSource 上要调哪几个参数？
  2. 背景音乐为什么不能用同一套设置？
  3. 设置面板里的音量滑条，怎么和音频系统接起来？
参考答案第 3 章 · 音频技术｜第 8 章 · Slider

① 三个参数决定方向感。第一是 Spatial Blend，必须从 2D 拖到 3D 一端——在 2D 状态下声音没有位置，左右声道一样响，玩家当然分不清方向。第二是 Min Distance / Max Distance：Min 之内保持最响，Min 之外开始衰减，超过 Max 停止衰减。Min 设得太大会让近处的敌人和远处的敌人一样响，方向感就没了，一般设 3~8 米；Max 要按场景尺度设，不然隔着半张地图还能听见。第三是 Spread（扩散），控制声音在扬声器空间的传播角度，调小一点能让声源「更集中」，方向判断更准。
如果还嫌吵，再补一条：把不重要的音效（脚步、环境杂音）的 Volume 压低，只让枪声、脚步这类需要定位

② 背景音乐必须是 2D。BGM 没有空间位置，它的作用是铺底氛围。如果 Spatial Blend 拖到 3D，玩家走远一点音乐就衰减、换个位置音量就变，听起来像「音乐在场景某个角落放」，非常出戏。所以 BGM 的音源Spatial Blend 保持 2D（值为 0），同时勾 Loop、Load Type 选 Streaming（长音频边播边读，不占内存）。另外整个场景只有一个 Audio Listener，挂在主相机上，它是「耳朵」；如果场景里多挂了一个，引擎会警告并且声音会重复播放，听起来像有回声。

③ 滑条接音频。在设置面板放一个 Slider（Min 0、Max 1，取消 Whole Numbers），把它的 OnValueChanged 事件拖到某个管理脚本上的公有方法，方法参数是 float（滑条的 Value 正好是 float，能直接接上）。方法体里两件事：给音源赋 audioSource.volume = value（范围就是 0~1，按 0~100 赋值会被钳到 1），或者更好的是写进 Audio Mixer 的 exposed parameter，这样一次能控制一整组音效，而不是逐个音源改。要做「音乐 / 音效」两个独立滑条，就在 Mixer 里分两个 Group，各自暴露一个参数。想持久化的话，把值存进 PlayerPrefs，下次进游戏读回来。

第 6 题（7 空，14 分）· 台球：瞄准线与击球力度实验三

下面的脚本挂在球杆上。功能是：鼠标位置画出瞄准线，松开鼠标时按拖拽距离决定力度击球，并检测球离台面多高。

public class CueControl : MonoBehaviour
{
    public Transform cueBall;
    public LineRenderer aimLine;
    public float maxPower = 2f;

    private Vector3 mouseWorld;
    private Rigidbody rb;

    void Start()
    {
        rb = cueBall.GetComponent<Rigidbody>();
    }

    void Update()
    {
        // 鼠标的屏幕坐标 → 世界坐标
        mouseWorld = Camera.main.(1)(Input.mousePosition);

        Vector3 dir = (mouseWorld - cueBall.position).normalized;

        // 拖得越远，力度越大
        float power = Vector3.(2)(mouseWorld, cueBall.position);
        if (power > maxPower) power = maxPower;

        // 画瞄准线：起点在球心，终点沿方向延伸
        aimLine.(3)(0, cueBall.position);
        aimLine.(3)(1, cueBall.position + dir * 5f);

        if (Input.GetMouseButtonUp(0))
        {
            rb.(4) = dir * power * 3f;
        }
    }

    void FixedUpdate()
    {
        // 台呢摩擦：每个物理步把速度衰减一点
        rb.(4) *= 1f / (1f + 2f * Time.(7));

        // 向下打一条射线，看球离台面多高
        Ray ray = new Ray(cueBall.position, Vector3.down);
        (5) hit;
        if (Physics.(6)(ray, out hit, 10f))
            Debug.Log("离台面 " + hit.distance);
    }
}
A Distance　B ViewportToWorldPoint　C ScreenToWorldPoint　D SetWidth
E velocity　F Dot　G SetPosition　H RaycastHit
I position　J fixedDeltaTime　K Raycast　L deltaTime
参考答案
空答案为什么
(1)CScreenToWorldPoint 把屏幕像素坐标转成世界坐标。Input.mousePosition 给的是屏幕坐标（左下角原点、单位是像素），不转换的话算出来的方向和距离全是错的。ViewportToWorldPoint（B）是视口坐标（0~1 比例），起点不一样。
(2)AVector3.Distance(a, b) 返回两点间的实际距离，是个标量。这里要的正是「鼠标离球多远」，越远力度越大。用 Dot（F）得到的是投影长度，方向反了会变负，不适合当力度。
(3)GLineRenderer.SetPosition(下标, 位置) 设置线段的某个端点。下标 0 是起点、1 是终点，所以本空出现两次：一次设起点、一次设终点，两处都填它才算对。这是画瞄准线、轨迹线的标准写法。
(4)ERigidbody.velocity 是刚体速度向量，直接赋值就是「立刻给这个速度」，比 AddForce 更硬、更没有延迟，适合击球这种瞬时动作。本空出现两次（Update 里赋值、FixedUpdate 里衰减），两处都填它才算对。
(5)HRaycastHit 是射线的结果结构体，里面装着命中点 point、法线 normal、距离 distance。out hit 要求这里声明的类型必须和 Physics.Raycast 的输出参数类型一致，写成别的直接编译报错。
(6)KPhysics.Raycast(射线, out 命中信息, 最大距离) 发射线并检测。射线检测只判断「有没有碰到、碰到哪」，不产生物理反作用，所以不会把球弹飞——这正是它和 Collider 碰撞的根本区别。
(7)JTime.fixedDeltaTime 是物理步长，专门配 FixedUpdate 用。代码在 FixedUpdate 里，如果填 deltaTime（L），衰减量会随渲染帧率变化，同一杆球在不同机器上滚的距离不一样。FixedUpdate 里算物理量，一律用 fixedDeltaTime。

这题的三个坑：① (3) 和 (4) 都出现两次，只填对一处不给分；② (7) 在 FixedUpdate 里，很容易顺手选 deltaTime；③ ScreenToWorldPoint 和 ViewportToWorldPoint 都是「转世界坐标」，区别只在输入坐标系，属于同一类 API 的干扰项。

第 7 题（8 空，16 分）· 角色：朝向目标与动作切换实验四 + 课件 04

下面的脚本挂在角色身上。功能是：判断目标在身前还是身后、平滑转向目标、靠近目标时动作放慢、按开火键播开枪动作。

public class CharControl : MonoBehaviour
{
    public Transform target;
    public float moveSpeed = 3f;
    public float turnSpeed = 5f;

    private Animator anim;
    private Rigidbody rb;

    void Start()
    {
        anim = GetComponent<Animator>();
        rb = GetComponent<Rigidbody>();
    }

    void Update()
    {
        Vector3 to = (target.position - transform.position).normalized;

        // 点乘为负说明目标在背后
        if (Vector3.(8)(transform.forward, to) < 0)
            Debug.Log("目标在身后");

        // 朝向目标，平滑转过去
        Quaternion rot = Quaternion.(9)(to);
        transform.rotation = Quaternion.(10)(transform.rotation, rot, turnSpeed * Time.deltaTime);

        // 朝目标移动
        Vector3 next = Vector3.(11)(transform.position, target.position, moveSpeed * Time.deltaTime);
        rb.MovePosition(next);

        // 越接近目标，动作越慢
        float d = (target.position - transform.position).magnitude;
        anim.(12) = Mathf.(13)(d / 5f);

        if (Input.(14)("Fire"))
            anim.(15)("Shoot", 0.1f);
    }
}
A Cross　B Dot　C Euler　D LookRotation
E Lerp　F Slerp　G Translate　H MoveTowards
I Clamp01　J speed　K CrossFade　L GetButtonDown

空答案为什么
(8)BVector3.Dot 是点乘，结果为正说明夹角小于 90°，为负说明在后方。这是课件里判断前后关系的标准写法（if (Vector3.Dot(forward, v) < 0) print("在后方")）。用 Cross（A）叉乘得到的是同时垂直于两者的向量，用来求旋转轴或平面朝向，判断不了前后。
(9)DQuaternion.LookRotation(方向) 把一个方向向量转成对应的四元数朝向。输入必须是方向而不是目标位置，所以上面先算了 to。用 Euler（C）是从欧拉角构造，三步都不同，接不上。
(10)FQuaternion.Slerp(当前, 目标, t) 是四元数的球面插值，转动的角速度均匀，看起来顺。四元数必须用 Slerp，不能用 Lerp（E）——用线性插值会导致转速忽快忽慢，甚至出现翻转。用 Lerp 插位置没问题，插旋转是典型错误。
(11)HVector3.MoveTowards(当前, 目标, 最大步长) 匀速挪过去，永远不会越过目标点。和 Lerp 的区别在于：Lerp 是「每次走剩余距离的一部分」，会越走越慢、永远差一点点；MoveTowards 是「每次走固定距离」，到站就停，适合移动速度固定的角色。Translate（G）是相对自身坐标系平移，不吃目标位置。
(12)JAnimator.speed 是动画播放速度倍数，1 为正常、0.5 为半速。它控制的是「动画播多快」，不是「角色走多快」——这个区别很关键，改 speed 不会让角色位移变慢，只会让动作变慢。
(13)IMathf.Clamp01(值) 把结果夹在 0~1 之间。d / 5f 在距离超过 5 米时会大于 1，动画速度倍率大于 1 会变成快放，所以要夹住。本空是唯一一个纯「防止越界」的保险，去掉它代码能跑，但远处目标会让角色动作鬼畜。
(14)LInput.GetButtonDown("Fire")：按下那一帧返回 true，参数是 Input Manager 里定义的按钮名，不是 KeyCode。课件里 Input.GetButtonDown("Jump") 就是这个写法。用 KeyCode 系列（GetKeyDown）参数得传枚举，接不上字符串。
(15)KAnimator.CrossFade(状态名, 过渡时间) 从当前状态直接混合到目标状态，不需要在状态机里连转移线，适合「临时插播一个动作」。第二个参数 0.1 是混合时长，给 0 会硬切。注意这不是 SetTrigger——CrossFade 绕过了转移条件，直接按名字切。

这题的四个坑：① Slerp 与 Lerp 的取舍是最高频的错；② MoveTowards 与 Lerp 的区别（匀速到站 vs 越走越慢）；③ GetButtonDown 的字符串参数是按钮名不是键名；④ CrossFade 和 SetTrigger 都能切动画，但前者不需要状态机里连线。

三、游戏综合设计题40 分 · 不写代码

本大题三题均取自《课程设计执行计划书》的 20 个选题，答题时可以直接借用你自己项目（题目 1 太空射击）的经验，但要用通用说法讲。

第 8 题（10 分）· 节奏打击音乐游戏课设题目 18

选题要求：音符跟随音乐节奏下落，玩家在正确时机按键得分；有判定分级与连击；界面要随节奏动态生成。涉及技术：AudioSource 音乐同步、List 存储音符时间戳、UI 动态生成。

  1. （5 分）音符的「正确时机」以什么为基准来判定？为什么不用 Time.time？
  2. （5 分）一首歌几百个音符，数据怎么存、界面上的音符对象怎么管理？
参考答案题目 18 · 节奏打击音乐游戏

① 基准必须是音乐自己播到哪了。用 AudioSource.time 作为时间基准，不能用 Time.time（游戏启动到现在过了多久）或 Time.deltaTime 累加。原因有三个：一是音乐会被人为延迟——玩家点了开始、加载资源、再真正 Play()，中间那几百毫秒游戏时间在走、音乐没走，用 Time.time 判定就会整体偏移；二是暂停/恢复时音乐停了，游戏时间不一定停；三是音频解码本身有延迟，尤其是 mp3 这类有编码前导的格式，实际出声比 Play() 晚几十毫秒。
所以判定逻辑是：每帧读 audioSource.time，和谱面里音符的时间戳比差值。判定窗口分级：差值在 ±0.05 秒内是 Perfect，±0.12 秒内是 Good，超过就是 Miss（具体数值可按难度调）。另外一定要给玩家一个全局延迟校准选项——不同设备的音频输出延迟不一样，耳机和外放的偏移能差到几十毫秒，让他自己按几下取平均值，存进 PlayerPrefs。没有这个校准，再准的判定也会被设备拖垮。

② 数据用 List，对象用池。谱面在编辑器里做成一份数据（ScriptableObject 或 JSON），运行时读进 List<Note>，每个 Note 里存 时间戳、轨道号、类型。之所以用 List 而不是数组，是因为要频繁按下标取、还要按时间顺序遍历，List 的动态扩容和索引访问都合适；也不用 Dictionary，因为这里没有「按 key 查」的需求。
运行时不要一次性把所有音符都实例化——一首歌三百个音符全生成出来，界面会被三百个 UI 对象压住。正确做法是滑动窗口：只生成「未来 2 秒内会出现」的音符，过了判定线就回收。回收走对象池：预先 Instantiate 十几个音符预制体、立刻 SetActive(false) 存起来，需要时取一个、SetActive(true) 并设好位置，判完再关掉还回去。这样整个游戏的 UI 对象数量恒定在十几个，不会随时间增长。
UI 动态生成指的是音符的横坐标按轨道数均分（四轨就占 1/4 宽），纵坐标由「当前音乐时间与音符时间戳的差值」线性映射——差值越小越靠下。这个映射关系必须是纯函数，才能保证不同帧率下音符位置一致。

第 9 题（15 分）· 2D 街机格斗游戏课设题目 9

选题要求：两名角色近身对战，有轻重攻击、可格挡、有连招；判定要精准，不能出现「明明打中了却掉血」。涉及技术：Animator 状态机（精细的帧事件触发攻击判定）、BoxCollider2D 攻击盒与受击盒分离、输入缓冲区（Input Buffer）。

  1. （5 分）攻击判定应该在动作的哪一刻生效？用什么机制实现？为什么不能在按下按键的瞬间就判定？
  2. （5 分）「攻击盒」和「受击盒」为什么要分成两个碰撞体？不分会出什么问题？
  3. （5 分）「输入缓冲区」解决的是什么问题？怎么做？
参考答案题目 9 · 2D 街机格斗

① 判定要挂在动作的关键帧上，不是按键那一刻。玩家按下攻击键，角色先要有一个抬手的前摇（几帧到十几帧），然后才是打击生效的判定帧，最后是收招硬直。如果按键瞬间就判定伤害，就会出现「手还没挥出去对方已经掉血」，格斗游戏的手感立刻崩掉。实现机制是 Animation Event（动画事件）：在攻击动画的判定帧上插一个事件，事件回调里才打开攻击盒、结算伤害，判定结束再插一个事件把它关掉。这样判定的时间窗口由美术的动画帧决定，而不是由代码里的延时决定——动作改了、判定跟着改，不用重新调数字。
另一种做法是用协程里 WaitForSeconds(0.15f) 硬等，但那是「按时间猜」，一旦动画速度变化就会错位，不如帧事件可靠。

② 攻击盒和受击盒必须分开。受击盒（Hurtbox）挂在角色身上，始终存在，表示「我身上哪里能被别人打到」，一般比模型略大一点点，让玩家觉得好打；攻击盒（Hitbox）平时是关闭的，只在判定帧打开，表示「我这一拳打到哪里」，位置和大小随招式变化。分开之后，判定逻辑就变成「攻击盒与受击盒是否重叠」，一次 Overlap 查询就能出结果，不依赖物理引擎的碰撞回调。
不分开的后果：如果一个碰撞体既当身体又当攻击判定，那角色站着不动时也会「撞到」对方，双方会莫名其妙掉血；而且受击盒和攻击盒的尺寸要求是相反的（受击盒要略大、攻击盒只覆盖拳头），一个碰撞体满足不了。另外两个角色互相靠近时，两个身体碰撞体会产生物理推动，格斗游戏里角色应该能穿过对方，这也要求身体碰撞体不能参与物理推挤。

③ 输入缓冲解决「按早了」。格斗游戏的连招窗口很窄，玩家经常在上一个动作还没结束时就按了下一个键。如果没有缓冲，这次按键会被直接丢弃，玩家会觉得「我明明按了但没出招」，判定成「不跟手」。缓冲区的做法：按键时不是立刻执行，而是把「按了什么键 + 按下时的时间戳」存进一个小队列（容量 2~3 个就够）；每个动作结束、回到可行动状态时，去队列里找最近 N 帧内（比如 8 帧）有没有待执行的输入，有就立刻接上。这样玩家提前一点点按也能接出连招。
配套还要有输入缓冲的反面：卡帧（Hitstop）——命中瞬间把双方动画和物理暂停几帧（Time.timeScale = 0 或降低 animator 速度），打击感会明显变重。但要注意暂停期间要接受输入缓冲，否则连招会断。

第 10 题（15 分）· 海岛荒野生存探险课设题目 11

选题要求：一座可自由探索的海岛，有昼夜变化、有会追击玩家的野生动物、有采集与建造；氛围要让人感到孤独和压迫。涉及技术：Terrain（地形系统）、NavMesh 敌人寻路、第一/第三人称控制器、Audio Mixer 音效混音。

  1. （5 分）这座岛的地形怎么搭？从一块空地到「有山、有沙滩、有树林」，步骤是什么？
  2. （5 分）动物怎么在岛上追玩家？NavMesh 需要先做什么？遇到断崖、河流怎么处理？
  3. （5 分）「孤独和压迫」这个氛围怎么用声音做出来？为什么需要 Audio Mixer 而不是直接改音量？
参考答案题目 11 · 海岛荒野生存

① 地形三步走。先导入 Environment 包建出 Terrain，尺寸按岛的规模定（比如 500×500）。造型用「先定基准、再堆细节」：Set Height 设一个基准高度 → Flatten 把整片抬平 → Raise/Lower 堆出中央山脉 → 用 Smooth 把山脚修成缓坡。海岸线的做法是把边缘刷低到接近水平面，再用水面（或 Terrain 的湖水功能）盖住，就有了沙滩到海的过渡。地表用 Paint Texture → Create Layer 分层：第一层沙滩作为基础层，往上叠草地、岩石、泥土，用画刷按高度和坡度刷——山脚铺草、山顶露岩、海边是沙，视觉上自然分层。然后 Paint Trees / Paint Details 刷树林和草丛，一定要配合 Tree Distance 和 Detail Distance 控制绘制距离，否则几千棵树会把帧率吃光。最后加 WindZone（方向模式）让草和树动起来，海岛的风感靠这个。

② NavMesh 先烘焙，再谈追人。NavMesh 是「可行走区域」的预计算网格，必须先烘焙（Bake），NavMeshAgent 才知道哪里能走。烘焙前要把地形、岩石、建筑标记为 Navigation Static，再在 Navigation 面板里 Bake，调好 Agent Radius（体型越大值越大，决定它能挤过多窄的缝）和 Agent Height。
动物身上挂 NavMeshAgent，追击就是每帧把 destination 设成玩家位置——Agent 会自动绕开障碍物寻路，不需要自己写 A*。断崖和河流有两种处理：一是烘焙时就让这些区域不可行走（把水面设成 Not Walkable），动物会自动绕路，代价是它可能绕很远；二是用 Off Mesh Link 手动连一条「跳跃/涉水」的通道，让它在特定位置能跨过去，并配一个跳跃动画。想做出「追到悬崖边停下」的效果，就把断崖边缘排除在 NavMesh 外，Agent 走到边界自然停住。
性能上要注意：玩家离得远的动物关掉 Agent（enabled = false）或降低更新频率，不然一岛几十只动物同时寻路会卡。

③ 用 Audio Mixer 做分层，不是调音量。氛围的核心是「声音的远近和有无」，不是「声音大小」。做法是建一个 Audio Mixer，把声音分成几组：Ambience（环境底噪：海浪、风）、Foley（脚步、采集）、Creature（动物叫声）、Music（音乐），每组有独立的音量和效果。
「孤独感」靠 Ambience：海浪声全程铺底但音量压得很低，让玩家一直有环境存在感；「压迫感」靠 Creature：白天的鸟叫很稀疏，到了夜晚把 Creature 组的音量整体推高，加入低沉的呼吸声和远处的嚎叫，同时把 Ambience 压低——不是加声音，是换声音的配比。这一整套切换用 Mixer 的 Snapshot（快照） 实现：做一个「白天」快照、一个「夜晚」快照，切换时用 TransitionToSnapshots 平滑过渡，几行代码就能完成整套氛围切换。
为什么不能直接改 AudioSource.volume：场景里可能有几十个音源，逐个改既麻烦又会漏；而且「同时降低所有环境音」这种需求在没有分组的情况下做不出来。Mixer 的意义就是把音量管理从「一个个音源」提升到「一个个类别」。另外空间感上，海浪用 2D（不需要方向），动物叫声必须用 3D + Min/Max Distance，玩家才能靠听判断它从哪个方向来——这恰恰是压迫感的来源。
